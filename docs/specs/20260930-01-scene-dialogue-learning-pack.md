## 0. 結論(先講結論)

```
現況:  照片 ──► 物品/區域辨識 ──► 單字卡 + 3 種練習      (辨識強,但「單字是孤立的」)
改版:  照片 ──► 物品/區域辨識 ──► 單字卡 + 3 種練習      (原封不動)
                  └─► 場景理解 ──► 3~5 句沉浸對話 ──► 文法小卡 + 對話練習   (新增)
```

1. **不動既有辨識管線**(你判斷辨識度已高,它是資產;改版不得讓它退化)。
2. **對話不依賴照片有人**。沒有人的照片用虛擬角色(店員/朋友),有人的照片只把人當「角色錨點」。
3. **人臉只做「偵測後模糊」,不做「識別」**,且在**裝置端上傳前**完成 —— 原圖不離開手機。
4. **對話為「延遲生成」**:舊學習包可事後補生成,不需重跑整包。
5. 每個對話含 **1 個文法重點**,並強制引用該學習包內的單字,讓「單字 → 情境」形成閉環。
6. 分 4 期:P0 驗證(Spike)→ P1 唯讀對話 → P2 對話練習 → P3 語音角色扮演。

## 1. 目標與非目標

### 1.1 目標(可量化,見第 12 節)

| # | 目標 | 衡量 |
|---|---|---|
| G1 | 從「認得單字」進到「會在情境中用」 | 對話完成率、對話練習正確率 |
| G2 | 對話難度貼合所選年級 | 黃金集人工評分「level fit」≥ 4.0 / 5 |
| G3 | 不增加隱私風險,且比現況更安全 | 上傳圖片 0 張含可辨識人臉 |
| G4 | 成本可控 | 單包新增 AI 成本 ≤ US$0.005(目標值,待 P0 實測) |
| G5 | 既有辨識品質不退化 | 黃金集物品辨識 F1 與改版前差 ≤ 1 個百分點 |

### 1.2 非目標(本期明確不做)

- 不做人臉**識別**(不判斷「這是誰」)、不推測年齡/性別/族群/親屬關係。
- 不做開放式自由聊天(AI 聊天機器人)。對話是**預先生成、可驗證的固定腳本**。
- 不做多人連線/分享對話(P3 之後再議)。
- 不改「基礎/進階」分級邏輯與 KK 音標邏輯。

## 3. 產品設計

### 3.1 系統管線(新增部分標 ★)

```
【裝置端】
 拍照/相簿
    │
    ▼
 ★A. 人臉偵測(僅 detect,不 recognize)
    │      iOS: Vision  /  Android: ML Kit Face Detection
    ▼
 ★B. 模糊處理 ──► 「去識別照片」(唯一會上傳的版本)
    │           原圖只留在本機(相簿/暫存),不上傳
    ▼
════════════════════ 上傳 ════════════════════
【雲端】
 S2  物品/區域辨識(既有,不改)──► words[] / regions[]
 S6  例句(既有,不改)
 ★S7 場景理解(含圖)──► scene{} / people[](只有框與外觀描述,無身分)
 ★S8 情境對話生成(純文字)──► dialogue{}
 ★S9 驗證器(純程式,不呼叫 LLM)
        ├─ 通過 ─────────────► 寫入學習包
        ├─ 失敗 ─► 重試 1 次 ─► 通過則寫入
        └─ 仍失敗 ─► 降級:樣板對話(不含 AI 自由文字)或隱藏功能
```

**S7 是否併入 S2?** 併入省一次圖片 token,但有讓 S2 辨識退化的風險(違反 G5)。

- 預設:**獨立 S7**(保護既有資產)。
- 判準:P0 以黃金集實測,若「S2 併入 scene/people 後物品 F1 差 ≤ 0.5 個百分點」才併入。

### 3.2 關鍵決策(含反方最強論證)

| # | 決策 | 反方最強論點 | 為什麼仍這樣選 | 怎麼驗證 |
|---|---|---|---|---|
| D1 | 對話**不依賴人物**,人物僅為角色錨點 | 「照片有人才有沉浸感,沒人就是憑空編故事」 | 使用者拍的多半是食物/物品(見 E1~E2),強制要人會讓多數照片沒有對話功能;虛擬角色 + 物品錨點同樣可沉浸 | P0:30 張黃金集中,無人照片的對話評分不低於有人照片 0.3 分以上 |
| D2 | 人臉**去識別在裝置端** | 「伺服端模糊實作簡單,少一套客戶端程式碼」 | 伺服端模糊 = 原圖已離開手機,隱私承諾變成「相信我們」而非「無法取得」。照片含兒童(E7) | 抓包驗證:上傳 payload 解碼後人臉區域已模糊 |
| D3 | 角色用**標籤**(Waiter / Friend / You),不用身分 | 「用『媽媽』『小明』更親切」 | 影像推斷親屬關係必然會猜錯,且屬敏感推測;標籤 + 使用者自選角色即可達到代入感 | 驗證器:對話中不得出現專有人名與親屬稱謂(黑名單 + 白名單角色) |
| D4 | 對話**延遲生成**(進學習包後按鈕/自動背景) | 「一次生成最省事,使用者不用等第二次」 | 舊包可補生成;失敗不拖垮主流程;可依使用者要不要對話節省成本 | 舊包(t-1.3.0)開啟後可生成,不重跑 S2 |
| D5 | 對話為**固定腳本 + 驗證器** | 「開放式聊天更沉浸、更靈活」 | 兒童使用,需可預期的內容;可預先審核、可離線重播、成本固定 | 驗證器通過率、黃金集人工評分 |
| D6 | 每包**1 個文法重點** | 「多教幾個文法更划算」 | 3~5 句容納不了多個重點,會變成文法清單,不是對話 | 每句標記 `usesPattern`,驗證器檢查 |
| D7 | 對話必須引用學習包單字(≥ 3 個) | 「對話自然最重要,別被單字綁住」 | 綁單字才讓兩個功能互相強化;不綁 = 兩個不相干功能 | 驗證器檢查 `wordRefs` |
| D8 | 免費層**不處理含人像照片**(待查證,見 §7.3) | 「免費層夠用,不要增加成本」 | 兒童照片一旦被用於產品改進,不可回收 | 法遵查證結論 |

## 4. 難度矩陣(對話規格,初版假設,以黃金集調參)

「句」= 一個發言(turn)。使用者要求 3~5 句。

| 難度 | 內部代碼* | 句數 | 每句字數上限 | 文法重點範例 | 對話形態 |
|---|---|---|---|---|---|
| 國小一到三年級 | `elem_low` | 3 | 6 | What's this? / It's a … / I like … | 問答式 |
| 國小四到六年級 | `elem_mid` | 4 | 9 | Can I have …? / There is / are … | 點餐、詢問 |
| 國小升國中 | `elem_up` | 4~5 | 12 | Would you like …? / I'd like … / because | 邀請與回應 |
| 國中 | `jr` | 5 | 15 | be going to / if / 比較級 | 計畫、比較 |
| 高中 | `sr` | 5 | 20 | 關係子句 / would / 現在完成式 | 表達意見 |

\* 只有 `elem_mid` 在截圖中出現(E5),其餘代碼為暫擬,以現行為準。

通用約束(驗證器強制):

- 句數在範圍內;每句字數 ≤ 上限
- 引用本學習包單字 ≥ 3 個(單字少於 3 個時放寬為全部)
- 只出現 `roles[]` 內定義的角色;無專有人名、親屬稱謂
- 每句都有繁體中文翻譯;英文句無中文夾雜
- 文法重點:`grammar.pattern` 必須在 `usesPattern` 所列的句子中真的出現(字串/樣式比對)
- 內容安全:過濾暴力、成人、政治、個資字詞

## 5. 資料合約(學習包 schema 擴充,以下為提案)

版本:模板 `t-1.3.0 → t-1.4.0`、prompt `pp-1.0.x → pp-1.1.0`、API `0.1.0 → 0.2.0`。
**向下相容**:沒有 `scene / dialogue` 欄位的舊包必須照常顯示。

```jsonc
{
  "templateVersion": "t-1.4.0",
  "words": [ /* 既有,不動 */ ],
  "regions": [ /* 既有,不動 */ ],

  "privacy": {
    "facesBlurredOnDevice": true,        // 由客戶端聲明;伺服器不信任但記錄
    "blurEngine": "vision|mlkit",
    "faceCount": 2                       // 只記數量,不記位置以外的任何屬性
  },

  "scene": {
    "titleEn": "Lunch at a small restaurant",
    "titleZh": "在小餐館吃午餐",
    "settingEn": "Two children eat lunch with soup and side dishes.",
    "settingZh": "兩位小朋友和湯、小菜一起吃午餐。",
    "roles": [
      { "id": "r1", "labelEn": "Waiter", "labelZh": "店員",
        "anchor": { "type": "virtual" } },
      { "id": "r2", "labelEn": "You",    "labelZh": "你",
        "anchor": { "type": "person", "ref": "p1" } }
    ]
  },

  "people": [                            // 可為空陣列
    { "id": "p1", "box": [ymin, xmin, ymax, xmax],   // 0~1000 正規化
      "look": "child in a blue shirt" }               // 只描述外觀,不描述身分
  ],

  "dialogue": {
    "id": "d1",
    "level": "elem_mid",
    "grammar": {
      "pattern": "Can I have …?",
      "titleZh": "請求東西的說法",
      "explainZh": "Can I have + 東西 = 我可以要…嗎?",
      "usesPattern": ["t2"]
    },
    "turns": [
      { "id": "t1", "role": "r1",
        "en": "Would you like some soup?", "zh": "你想喝點湯嗎?",
        "wordRefs": ["w5"] },
      { "id": "t2", "role": "r2",
        "en": "Yes, can I have some cabbage too?", "zh": "好,我也可以要一些高麗菜嗎?",
        "wordRefs": ["w2"] }
    ],
    "practice": {
      "cloze":   [ { "turnId": "t2", "blank": "cabbage", "distractors": ["sausage", "plate"] } ],
      "reorder": [ { "turnId": "t2" } ]
    }
  },

  "meta": {
    "promptVersion": "pp-1.1.0",
    "dialogueStatus": "ready|pending|failed|skipped",
    "cost": { "stage": "S8", "inTokens": 0, "outTokens": 0 }
  }
}
```

規則:

- `wordRefs` 必須指向存在的 `words[].id`(驗證器檢查)。
- `people.box` 只在客戶端用來畫高亮,**不裁切圖卡**。含人像區域的圖卡一律取自**去識別照片**。
- `dialogueStatus` 讓客戶端決定顯示「產生對話 / 產生中 / 重試 / 不支援」。

### 5.1 API(提案)

| 方法 | 路徑 | 說明 |
|---|---|---|
| POST | `/packs` | 新增 `options.includeDialogue`(預設 true)、`privacy.facesBlurredOnDevice` |

## 6. AI 設計

### 6.1 S8 輸入(純文字,不再傳圖)

```
輸入:  scene.setting, scene.roles, words[](id, en, zh, group), level 規格(第 4 節)
輸出:  dialogue JSON(response schema 強制)
不給:  原始照片、people.look 以外的任何人物資訊
```

純文字階段成本量級與 S6 相近(E4:1,265 in / 303 out),**這是推測**,以 P0 實測為準。

### 6.2 Prompt 原則

1. 先給角色與場景,再給單字清單,最後給難度規格與文法目標。
2. 明確禁止:專有人名、親屬稱謂、年齡/性別/族群推測、照片外的事實。
3. 要求輸出前自檢:句數、字數、單字引用、文法句。**但不信任自檢**,以 S9 驗證器為準。
4. 溫度偏低,追求穩定而非創意。

### 6.3 S9 驗證器(純程式,可單元測試)

| 檢查 | 失敗處理 |
|---|---|
| JSON schema 合法 | 重試 |
| 句數/字數/單字引用/文法句 | 重試(附上失敗原因回饋 prompt) |
| 黑名單(人名、親屬、敏感詞) | 重試 |
| 重試後仍失敗 | 降級為樣板對話,或 `dialogueStatus=failed` 並顯示「稍後再試」 |

## 7. 隱私與安全

### 7.1 名詞界定(團隊必須一致)

| 名詞 | 是什麼 | 本案 |
|---|---|---|
| 人臉**偵測** Face Detection | 找出「哪裡有臉」(框) | ✅ 只用於模糊 |
| 人臉**識別** Face Recognition | 判斷「這是誰」、比對特徵 | ❌ 不做、不儲存特徵 |
| 屬性推測 | 年齡、性別、情緒、族群 | ❌ 不做 |

> 我對「去除人臉識別」的解讀是「不做 Recognition;Detection 僅用於模糊」。若你的意思是連偵測都不要,則需改為「整張照片不上傳含人像者」,見第 14 節 Q1。

### 7.2 資料流

```
原圖 ──(留在本機)
  └─► 偵測 ─► 模糊 ─► 去識別照片 ─► 雲端(GCS/Storage)─► 圖卡裁切也來自去識別照片
```

- 預設**開啟**且可在設定中關閉?→ 建議**不提供關閉**(未成年人使用情境),見 Q3。
- 偵測不到臉(側臉、遮擋、小臉)時的策略:**寧可多模糊**;偵測信心閾值取寬鬆值,並保留「手動框選模糊」補救入口(P2)。
- 模糊強度須使人臉不可還原(高斯模糊 sigma 足夠大或馬賽克),不可只降透明度。

### 7.3 待查證事項(我本次未查證)

| # | 事項 | 為何重要 | Owner |
|---|---|---|---|
| V1 | Gemini API **免費層**的內容是否可能被用於產品改進(截圖顯示目前實付 US$0 = 免費層) | 若是,含兒童的照片不應走免費層 | Backend/AI + 法遵 |
| V2 | 台灣個資法對未成年人影像的要求、App Store / Google Play 兒童類別政策 | 上架合規 | PM + 法遵 |
| V3 | 各平台 SDK 的人臉偵測在本機是否**完全離線**執行 | D2 的前提 | Mobile |

### 8.5 互動規格

| 元件 | 行為 |
|---|---|
| 對話句氣泡 | 點擊 = 播放該句 TTS + 照片上高亮該句 `wordRefs` 對應物品 |
| 句中單字連結 | 點擊 = 開該單字卡(既有卡片的 bottom sheet),含「+單字簿」 |
| 中文翻譯 | 預設顯示;設定可切「點擊才顯示」(進階學習者) |
| 「全部播放」 | 依序播放,播放中該句高亮;可暫停;速度 0.8× / 1× |
| 角色切換 | 選「你扮演」的角色;該角色的句子在練習時由使用者念 |
| 文法小卡 | 顯示 `pattern` + 一行中文說明 + 對應句子標色 |
| 產生中 | 骨架屏 + 文案「正在為這張照片編對話…」,可離開,完成後於膠囊顯示小圓點 |
| 產生失敗 | 顯示「暫時無法產生對話」+「重試」按鈕;不影響其他模式 |
| 舊包尚無對話 | 顯示「為這張照片產生情境對話」主按鈕 |

### 8.6 視覺與無障礙(沿用團隊既有規範)

- 觸控目標 ≥ 44×44pt;文字對比 WCAG AA(4.5:1)。
- 圖示一律向量圖示(不使用 emoji)。
- 支援系統字級放大(Dynamic Type / Font Scale),氣泡自動增高、不截字。
- 螢幕閱讀器:氣泡朗讀「角色:句子;翻譯:…」;高亮不只依賴顏色(加外框粗細變化)。
- 遵守系統「減少動態效果」設定。
- TTS 使用裝置內建語音(沿用現有聲明);品質因裝置而異,頁尾維持現有免責文字。

### 8.7 空狀態與錯誤狀態清單(Design 需交付)

| 狀態 | 需設計 |
|---|---|
| 無人物照片 | 角色列顯示虛擬角色,不出現「人物」字樣 |
| 有人物、模糊後仍可辨 | 不影響 |
| 單字 < 3 個 | 對話仍生成,但降低引用門檻;或顯示「單字太少,無法編對話」 |
| 離線 | 已生成的對話可讀;TTS 為本機語音,可用;生成按鈕停用並說明 |
| 生成中/失敗/逾時 | 見 8.5 |

|---|---|---|---|
| **P0 Spike**(規模 S) | ① 30 張黃金集(食物/桌面/戶外/有人/無人/多人各 5)② S8 prompt 實驗 ③ 裝置端人臉模糊 POC ④ 標記命中率量測(B1)⑤ S7 併入 S2 的 A/B ⑥ 免費層條款查證(V1) | 實驗報告、黃金集、驗證器原型 | **Gate G0**:人工評分 level fit ≥ 4.0、驗證器一次通過率 ≥ 85%、上傳圖 0 張含可辨識人臉、V1 有結論 |
| **P1 MVP**(規模 M) | schema t-1.4.0、S7~S9、`POST /packs/{id}/dialogue`、對話頁(閱讀/TTS/高亮/文法卡)、新增頁加「內容」、舊包補生成、設定開關、功能旗標 | 可上 TestFlight/內測版 | **Gate G1**:見 §11 驗收;E2E 綠燈;成本符合 G4 |
| **P2 練習**(規模 M) | 填空、重組、輪流角色扮演、寫入單字簿、手動補模糊 | 版本 +1 | 練習完成率、答對率資料可回傳 |
| **P3 語音**(規模 L) | STT 語音角色扮演、同照片多情境/重新生成變體 | 版本 +1 | 語音辨識可用率、成本評估 |

規模為相對大小(S<M<L),人週請由團隊依實際人力估算 —— 我沒有你們的速度資料,不編數字。

工程紀律(沿用團隊規則):

- TDD:先寫驗證器與 schema 測試,再寫生成邏輯(Red → Green → Refactor)。

- TypeScript 若為實作語言:零 `any`;LLM 輸出一律 `unknown` + 型別守衛/schema 驗證後才使用。
- 功能旗標:`dialogue.enabled`、`privacy.blur.enforced`,可分階段對內測用戶開放。

## 12. 成本與指標

### 12.1 成本

- 基準:現況單包 AI 成本 US$0.0091(E4,含雲端運算推估)。
- 新增:S7(含圖,量級近 S2 的輸入)+ S8(純文字,量級近 S6)。
- 目標:單包新增 ≤ US$0.005(G4)。**這是目標值,不是預估**,P0 用既有成本面板實測。
- 節流:對話延遲生成 + 冪等快取(同包同難度不重複扣款);重新生成有每日上限。

### 12.2 產品指標

| 指標 | 定義 | 用途 |
|---|---|---|
| 對話開啟率 | 有對話的包中,使用者開啟對話頁的比例 | 功能價值 |
| 對話完成率 | 播放/閱讀到最後一句 | 內容適配度 |
| 對話→單字簿轉換 | 從對話加入單字簿的單字數 | 閉環是否成立 |
| 生成成功率 | 驗證器最終通過(含重試)/ 請求數 | 穩定度(目標 ≥ 98%) |
| 一次通過率 | 未重試即通過 | prompt 品質(目標 ≥ 85%) |
| p95 生成延遲 | 請求到 `ready` | 體驗(目標待 P0 定) |
| 單包成本 | 依成本面板 | G4 |
